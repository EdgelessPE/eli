# ELI Loader 与 LoadScreen Play 软件设计文档（SDD）

## 1. 文档信息

- 状态：设计草案
- 日期：2026-09-10
- 范围：Windows Edgeless PE 启动流程、`eli loader`、`loadscreen play`
- 关联文档：`docs/loadscreen-bake-requirements.md`

## 2. 背景

当前 PE 通过 `Pecmd.ini` 组织启动流程。后续计划使用 Rust 实现 `eli loader`，逐步接管其中与 Edgeless 有关的启动逻辑，同时保留 PECMD 作为 PE 环境下的命令执行后端。

`loadscreen bake` 已负责把加载动画切片打包为带进度标记的 WebP 文件。下一步的 `loadscreen play` 不仅要按整体启动进度选择画面，还要在画面上显示百分比、当前正在加载的内容，并预留展示完整任务列表的能力。

启动进度不能由一组固定阶段百分比组成。Loader 应先扫描本次启动涉及的任务，根据插件包的文件大小和属性等外部元数据动态估算每项任务的权重，再按权重之和计算整体进度。

## 3. 设计目标

1. 用 Rust 中的类型化流程描述 PE 启动步骤，达到类似 `pecmd.lua` 或 `startnet.cmd` 的可读性和可维护性。
2. 不重新实现完整 PECMD；不适合原生重写的行为继续调用 PECMD。
3. 启动前只依据文件系统元数据和配置生成完整、不可变的执行计划。
4. 所有任务都拥有动态权重，不使用固定的阶段百分比区间。
5. Loader 是进度和任务状态的唯一事实来源，Play 只负责展示。
6. Play 只接收语义进度和展示任务状态，不感知 `lsbp` 文件名、切片数量或 Loader 的执行参数。
7. 执行模型与展示模型分离，为未来显示完整任务列表保留稳定接口。
8. 支持插件并行加载、失败隔离、可靠的进度汇总和确定性的 UI 状态。
9. Play 启动或通信失败不得阻塞 PE 正常启动。

## 4. 非目标

首版不包含以下能力：

- 实现一个通用 PECMD 解释器或完整替代 PECMD。
- 引入 YAML、TOML 等通用启动工作流语言。
- 解压、列举或读取插件包内部内容来估算进度，包括调用 `7z l`。
- 执行期间重新估算权重、修改计划或追加动态任务。
- 根据实测耗时自动训练或持久化权重模型。
- 要求首版 Play 显示完整任务列表；首版只需保存完整状态并显示当前内容。
- 在 Linux 或 macOS 上实现 PE 启动画面的实际播放窗口。
- 首版强制实现帧间淡入淡出等高成本动画效果。

## 5. 总体架构

```text
启动配置与文件系统
        │
        ▼
   BootPlanner ───────► ExecutionPlan
        │                    │
        │                    ▼
        └────────────► DisplayPlan
                             │
ExecutionPlan                │
        │                    │
        ▼                    │
   BootExecutor ──LoaderEvent┴──► ProgressHub
        │                              │
        ├── Rust 原生任务               ▼
        ├── PecmdBridge           LoadScreen Protocol
        └── 其他外部程序                  │
                                       ▼
                              Transport ──► Play
```

依赖方向必须保持单向：

- `BootPlanner` 不依赖 Play、Slint 或通信方式。
- `BootExecutor` 只产生领域事件，不直接操作 UI。
- `ProgressHub` 汇总事件并维护完整展示状态，是整体进度的唯一事实来源。
- 协议层只包含纯数据，不包含执行闭包、文件路径、PECMD 参数或权重算法。
- Play 不读取 Loader 内部状态，也不自行根据任务权重计算整体进度。

## 6. Loader 与 PECMD 的职责边界

### 6.1 Loader 的定位

`eli loader` 是一个类型化的启动脚本和流程控制器，而不是新的脚本语言。它负责：

- 扫描本次启动需要执行的工作。
- 建立执行计划和展示计划。
- 安排步骤顺序和允许的并发关系。
- 调用 `eli-lib` 中已有的原生能力。
- 通过统一桥接层调用 PECMD 或其他外部程序。
- 汇总错误、任务状态和整体进度。
- 管理 LoadScreen Play 生命周期与通信。

Loader 应直接调用 `eli-lib` API，不应在同一进程内递归启动 `eli` CLI。CLI 只负责参数解析、上下文初始化和命令转发。

### 6.2 PECMD 的定位

PECMD 继续作为 Windows PE 的执行后端，以下行为无需在首版 Rust Loader 中重新实现：

- `MAIN`、`INIT`、`SHEL` 等 PECMD 核心初始化命令。
- 与桌面、Shell、注册表或 PECMD 自身状态强耦合的命令。
- 已经稳定存在于 `.wcs`、`.ini` 中且重写收益较低的流程。
- 其他实现成本高、兼容风险大或缺乏可靠替代方案的命令。

Loader 可以按步骤调用 PECMD 单条命令，也可以通过固定的 `.wcs`/`.ini` 桥接脚本调用一组命令。目标是逐步翻译现有 `Pecmd.ini` 的控制流程，而不是一次性消除 PECMD。

### 6.3 统一外部执行接口

PECMD 调用应集中在 `PecmdBridge` 或通用外部执行器中，避免业务模块散落字符串拼接。每次调用至少需要明确：

- 是否等待进程完成。
- 是否隐藏窗口。
- 是否允许进程脱离 Loader 后继续运行。
- 工作目录和显式传入的环境变量。
- 超时时间。
- 失败策略。

外部可执行文件必须通过 `eli-lib` 的通用依赖管理模块从 `PATH` 解析并验证。Windows PE 专属逻辑必须在发生副作用前验证运行环境，并通过条件编译隔离平台实现。

### 6.4 全局状态与并发

修改桌面、Shell、全局注册表、PECMD 全局变量等共享状态的 PECMD 步骤默认串行执行。只有明确证明互不影响的任务才允许并行。

Loader 自身的状态保存在 `LoaderContext` 中。并发任务所需环境变量通过子进程参数显式传递，不使用进程级环境变量作为线程间通信手段。

仅用于旧脚本间传参的临时文件不应机械保留，应改为函数参数、结构体或子进程参数。确实存在其他进程消费者的恢复标记或持久配置则继续兼容。

## 7. 两阶段启动模型

Loader 分为规划和执行两个阶段。

### 7.1 规划阶段

规划阶段是只读扫描，允许读取：

- 插件包路径、文件大小和普通文件系统元数据。
- 插件包扩展名或外部属性，例如普通预加载、LocalBoost、未来的按需加载、冻结等。
- `repoPart.txt` 等仍由多个组件共同使用的持久配置。
- 决定启动步骤是否启用的全局配置。

规划阶段禁止：

- 解压插件包。
- 枚举压缩包内部文件。
- 读取压缩包内部清单、脚本或元数据。
- 调用 `7z l` 等变相内部扫描命令。
- 执行会改变系统状态的启动步骤。

规划完成后生成并冻结 `LoadPlan`。执行开始后不得改变任务集合、顺序关系和权重。

在计划尚未冻结时，Play 可以停留在 `0.0%` 并显示“正在分析启动任务”。计划冻结后，Loader 先发送完整展示计划，再从 `0.0%` 开始发送执行更新。

### 7.2 执行阶段

`BootExecutor` 按 `ExecutionPlan` 执行任务。任务可以是：

- Rust 原生函数。
- PECMD 命令或脚本。
- CMD、WinXShell 或其他外部程序。
- 由若干内部步骤组成的插件加载任务。

每个步骤开始、成功、失败或跳过时产生 `LoaderEvent`，由 `ProgressHub` 统一归并。工作线程不得直接向 Play 发送状态，以避免消息乱序和 UI 状态竞争。

## 8. 动态权重模型

### 8.1 基本原则

权重表示任务的相对预计成本，不是百分比。不存在“初始化占 10%”“插件占 70%”这样的固定区间。

每种任务根据扫描结果调用自己的估算器：

```rust
trait LoaderTask {
    fn estimate_weight(&self, context: &ScanContext) -> NonZeroU64;
    fn execute(&self, context: &ExecutionContext) -> TaskResult;
}
```

计划模型可抽象为：

```rust
struct LoadPlan {
    tasks: Vec<PlannedTask>,
    total_weight: u64,
}

struct PlannedTask {
    id: TaskId,
    display_task_id: DisplayTaskId,
    weight: NonZeroU64,
    action: TaskAction,
    failure_policy: FailurePolicy,
}
```

实际实现可以调整字段，但必须维持“逐任务估算、计划冻结、总权重求和”的语义。

### 8.2 插件权重估算

插件包仅按文件大小和外部属性估算。推荐的基础形式为：

```text
任务权重 = 类型基础成本 + ceil(文件大小 / 大小单位) × 类型大小系数
```

普通预加载、LocalBoost、按需加载和冻结插件分别使用不同的估算器或系数：

- 普通预加载：估算准备、解压、发布和脚本执行成本。
- LocalBoost：额外估算仓库准备、合并或链接等步骤。
- 按需加载：启动时只计算注册或建立索引的成本，不预支未来真正加载的成本。
- 冻结插件：如果启动时不需要执行，则不生成加载任务；如仍需登记，可生成很小的登记任务。

估算公式中的常量是成本模型参数，不是固定进度百分比。后续可以独立调优，而不改变进度协议。

### 8.3 减少进度跳跃

为了避免“每个插件只完成一次”导致进度大幅跳跃，规划器可以在不读取包内容的前提下，把已知加载管线拆成多个可完成步骤。例如：

```text
普通插件：准备 → 解压 → 发布 → 执行脚本
LocalBoost：仓库准备 → 解压 → 合并/链接 → 发布 → 执行脚本
按需加载：登记
```

这些步骤仍然只依据文件大小和插件属性估算权重。首版不根据运行时耗时修正剩余权重。

### 8.4 整体进度计算

```text
总权重 = Σ 所有计划任务的权重
已完成权重 = Σ 所有已进入终态任务的权重
整体进度 = floor(已完成权重 × 1000 / 总权重) / 10
```

内部推荐使用 `0..=1000` 的整数表示十分之一百分比，并在乘法中使用更宽的整数类型避免溢出。对外协议发送 `0.0..=100.0` 的语义百分比。

整体进度必须单调不减。只有计划内全部任务进入终态后才能发送 `100.0%`。

失败和跳过也是终态，应结算该任务的计划权重，使启动完成时进度能够到达 100%。错误是否中断启动由失败策略单独决定，不能由进度值表达。

### 8.5 并发结算

并发任务独立报告事件，`ProgressHub` 单点维护任务状态和已完成权重：

- 每项任务的权重最多结算一次。
- 重复或迟到的终态事件不得重复增加进度。
- 多个插件包可以并行，单包失败不回滚其他包。
- 同一插件包内部仍保证 CMD 脚本早于 WCS 脚本。
- 不在不同插件包之间建立全局 CMD/WCS 阶段屏障。

## 9. 执行计划与展示计划解耦

### 9.1 ExecutionPlan

`ExecutionPlan` 是 Loader 的内部模型，允许包含：

- Rust 函数或命令类型。
- PECMD 参数和脚本路径。
- 依赖关系、串并行约束、超时和失败策略。
- 动态估算权重。
- 仅供诊断使用的内部步骤。

该模型不得通过 LoadScreen 协议暴露。

### 9.2 DisplayPlan

`DisplayPlan` 是稳定的展示模型，只包含用户可理解的信息：

```rust
struct DisplayTask {
    id: DisplayTaskId,
    parent_id: Option<DisplayTaskId>,
    title: String,
    order: u32,
}

enum DisplayTaskState {
    Pending,
    Running,
    Succeeded,
    Failed,
    Skipped,
}
```

任务可以通过 `parent_id` 组成层级，为未来完整任务列表提供基础。标题需要做长度限制和字符清理，避免把不可信文件名直接无限制绘制到画面上。

### 9.3 多对一映射

多个内部执行任务可以映射到一个展示任务。例如：

```text
展示任务：加载插件：7-Zip
内部任务：准备 → 解压 → 发布 → 执行脚本
```

内部步骤切换时，只更新展示任务的 `detail`，例如“正在解压”或“正在执行启动脚本”。这样既能提供细腻的进度，又不会把实现细节固化为 UI 协议。

## 10. LoadScreen 通信协议

### 10.1 协议职责

协议用于同步：

- 本次会话的完整展示任务列表。
- 权威的整体百分比。
- 当前聚焦任务。
- 任务状态和当前详细内容。
- 最终完成状态。

协议不传递：

- `lsbp` 文件名或切片编号。
- 插件包真实路径。
- PECMD 命令行或环境变量。
- 内部任务权重和权重公式。
- Rust 执行动作或 UI 组件类型。

### 10.2 消息类型

计划消息在执行更新前发送一次：

```json
{
  "type": "plan",
  "version": 1,
  "tasks": [
    { "id": 1, "parent_id": null, "title": "初始化 Windows", "order": 0 },
    { "id": 2, "parent_id": null, "title": "加载插件", "order": 1 }
  ]
}
```

更新消息携带权威百分比和增量状态：

```json
{
  "type": "update",
  "seq": 18,
  "progress": 42.6,
  "focus_task_id": 2,
  "changes": [
    { "id": 2, "state": "running", "detail": "正在解压 7-Zip" }
  ]
}
```

结束消息表示会话完成，并可包含成功、带警告完成或失败等汇总结果。

### 10.3 顺序与可靠性

- `plan` 必须先于任何 `update`。
- 每个会话的任务 ID 保持稳定。
- `seq` 严格递增，用于识别重复、丢失或乱序消息。
- 任务状态变化必须可靠、有序传递，不得被随意丢弃或合并。
- 高频视觉进度可以只保留最新目标值，但不能覆盖尚未送达的任务终态。
- 若未来支持 Play 重启或重新连接，`ProgressHub` 应能够重发计划和完整状态快照。

### 10.4 发布接口

Loader 通过抽象发布器与具体通信方式解耦：

```rust
trait ProgressPublisher {
    fn publish(&mut self, message: LoadScreenMessage) -> Result<(), PublishError>;
}
```

建议至少提供：

- PE 环境使用的有序进程间通信实现。
- 单元测试使用的内存实现。
- 禁用 LoadScreen 或 Play 失败时使用的空实现。

首版可以根据进程所有权选择匿名管道或命名管道，但传输层不得改变上层消息语义。

## 11. Play 渲染模型

### 11.1 切片选择

Play 自行读取 `lsbp` 包并解析其中合法的 `lsbp_*.webp` 进度标记。Loader 永远不需要知道文件名和切片数量。

对于当前展示进度，Play 选择“不大于目标值的最大进度标记”对应的帧。由此可以兼容不同 `slices` 生成的包。

包至少应包含起点和终点帧，进度标记必须唯一且可排序。异常包应返回明确错误，不得因文件名异常而崩溃。

### 11.2 目标进度与展示进度

协议中的 `progress` 是 Loader 给出的权威目标进度。Play 维护独立的 `display_progress`：

- 平滑追赶最新的目标进度。
- 不回退。
- 不超过目标进度。
- 使用 `display_progress` 选帧和绘制数字。
- 收到 100% 后，等待画面追到 100% 再退出或进入结束状态。

平滑过渡只改变视觉表现，不改变 Loader 的真实任务状态，也不能虚构超过目标值的进度。

### 11.3 文本与任务展示

首版画面至少渲染：

- 当前百分比。
- 当前聚焦任务标题。
- 当前任务详细内容。

Play 内部仍保存全部 `DisplayTask` 及其状态。未来新增完整任务列表时，只需扩展视图，无需修改 Loader 的执行模型。

允许多个任务同时处于 `Running`。`ProgressHub` 根据确定性规则选择一个 `focus_task_id`，例如最近发生有效状态变化且仍在运行的任务。并发工作线程不能各自争抢 UI 焦点。

### 11.4 GUI 线程模型

Play 的业务状态由 Rust 维护，Slint 只渲染属性和用户界面。压缩包读取和图片解码不得阻塞 UI 事件线程；后台完成后通过 Slint 事件循环安全地提交结果。

首版优先使用适合 Windows PE 的软件渲染路径，并只缓存当前帧及少量相邻帧，避免一次性解码全部高分辨率图片。

## 12. 失败策略与降级

每个执行任务显式声明失败策略：

- `Fatal`：停止后续不安全或无意义的任务，进入失败收尾。
- `WarnAndContinue`：记录警告并继续启动。
- `Ignore`：仅记录诊断信息。

无论采用哪种策略，已经完成的任务不回滚，任务状态和结果必须进入最终汇总。

插件包是相互独立的加载任务。单包失败不得阻止或回滚其他插件包，最终统一汇总成功与失败结果。

LoadScreen 属于可降级组件：

- Play 启动失败时，Loader 继续启动流程并记录错误。
- 通信断开时切换到空发布器，避免不断阻塞或重试。
- Play 渲染异常不得影响 PECMD、插件加载或 Shell 启动。

## 13. 建议代码组织

遵循现有命令分层约束，建议按以下方向组织：

```text
eli-lib/src/command/loader/
  mod.rs
  plan.rs
  execute.rs
  progress.rs
  pecmd.rs

eli-lib/src/command/loadscreen/
  mod.rs
  play.rs
  protocol.rs

eli-cli/src/command/
  loader.rs
  loadscreen.rs
```

CLI 继续保持薄转发层。PE 特定的进程、管道和窗口实现通过条件编译隔离，由 `eli-lib` 提供统一入口；计划、权重、协议和状态归并逻辑保持平台无关，以便在 Windows、Linux 和 macOS CI 中运行单元测试。

当前 `loadscreen` 父命令不应整体受 `loadscreen-bake` 特性控制。引入 Play 时，应只对 `Bake` 变体及其重依赖进行特性裁剪，确保 PE 精简构建可以只携带 Play 所需能力。

## 14. 测试设计

### 14.1 规划与权重单元测试

- 只使用文件大小和外部属性生成插件任务，不读取包内内容。
- 不同大小、普通加载、LocalBoost、按需加载产生不同权重。
- 相同输入生成确定的任务顺序、ID、权重和总权重。
- 总权重等于全部任务权重之和，不发生零权重和整数溢出。
- 计划冻结后无法追加任务或修改权重。

### 14.2 进度与并发单元测试

- 按权重正确计算十分之一百分比。
- 并发终态事件只结算一次，进度单调不减。
- 失败和跳过任务正常结算权重。
- 只有所有任务进入终态后才产生 100%。
- 多个执行任务到一个展示任务的映射正确。
- 全局 PECMD 步骤保持串行，独立插件任务允许按窗口并行。

### 14.3 协议单元测试

- `plan` 必须先于 `update`。
- 协议版本、序列号和未知任务 ID 校验正确。
- 合法和非法状态迁移可被识别。
- 计划与完整状态快照能够恢复 Player 状态。
- 畸形输入、超长文本和未知字段不会导致崩溃。

### 14.4 Play 单元测试

- 不同切片数量均能按百分比选择正确帧。
- 非法、越界和非有限进度被安全处理。
- 展示进度不回退、不超越目标值。
- 百分比、聚焦任务和详细内容同步更新。
- 即使首版不绘制完整列表，也能保存全部任务状态。

### 14.5 端到端测试

端到端脚本统一放在 `tests/e2e/`，至少覆盖：

- Loader 启动 Play，发送计划、更新和结束消息。
- 使用不同 `slices` 的 `lsbp` 包完成播放。
- 并发插件任务的状态和最终汇总顺序正确。
- Play 启动失败或中途退出时 Loader 继续启动。
- Windows 环境验证实际软件渲染结果和进程生命周期。

平台无关的计划、协议和状态归并测试应在 Windows、Linux 和 macOS CI 中执行；Windows PE 专属执行和渲染行为在 Windows 对应测试中验证。

## 15. 首版实施顺序

1. 定义平台无关的 `ExecutionPlan`、`DisplayPlan`、任务状态和协议 DTO。
2. 实现只读扫描、插件属性分类和动态权重估算，并冻结计划。
3. 实现 `ProgressHub`、单点状态归并和内存发布器测试。
4. 建立 `PecmdBridge` 与统一进程策略，逐段翻译现有 `Pecmd.ini` 中的 Edgeless 流程。
5. 实现 Play 的 `lsbp` 自发现、百分比选帧、平滑展示和文字叠加。
6. 接入可靠有序的进程间通信，并实现 Play 失败降级。
7. 补齐 Windows PE 端到端验证和三平台公共逻辑 CI。

## 16. 已确认的关键决策

- Loader 采用 Rust 类型化流程，PECMD 保留为可调用执行后端。
- `MAIN`、`INIT`、`SHEL` 等不在首版重写范围内。
- 插件估算不打开、不解压、不列举压缩包内部内容。
- 每个任务独立动态估算权重，总进度分母由扫描后的权重之和决定。
- 首版不处理运行时估算纠偏和动态新增任务。
- Loader 向 Play 发送百分比、完整展示任务计划和状态变化，不发送帧文件名。
- 执行计划与展示计划分离，多个内部步骤可以映射为一个用户可见任务。
- Loader/ProgressHub 负责真实进度和任务状态，Play 负责选帧、平滑动画和文本渲染。
- 协议从首版起支持完整任务列表，即使首版界面只显示当前加载内容。
- LoadScreen 故障不得阻塞 PE 启动。
