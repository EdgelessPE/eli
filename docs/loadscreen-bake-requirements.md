# `eli loadscreen bake` 需求文档

## 1. 背景

LoadScreen 是 Edgeless 启动过程中的全屏进度展示能力。它以用户提供的壁纸为底图，在启动进度从 0% 变化到 100% 时切换不同模糊程度的图片，使背景逐步变清晰；真实进度信息由后续播放器叠加显示，不属于本命令职责。

`eli loadscreen bake` 负责将一张静态图片预先烘焙为若干张不同高斯模糊程度的 WebP 图片。本阶段只产出图片目录，不生成或读取 `.bin` 文件。

## 2. 目标

- 提供跨 Windows、Linux、macOS 的静态图片烘焙命令。
- 在保留输入图片分辨率的前提下，生成从最模糊到完全清晰的一组图片。
- 让相邻图片的目标高斯模糊强度随展示进度尽可能线性变化。
- 并发执行各图片的处理任务，并实时展示总体及各 job 的状态和进度。
- 通过 Cargo feature 隔离烘焙实现及其额外图片格式依赖，使 PE 精简构建可以排除相关命令和额外编解码能力。
- 使用事务式目录发布，避免失败或并发执行时留下不完整结果。

## 3. 非目标

本阶段不包含：

- 将烘焙结果打包为 `.bin` 文件。
- 播放烘焙图片。
- 采集、计算或渲染真实启动进度。
- 在图片中预先绘制进度文字、进度条或其他界面元素。
- GIF 或其他动画图片输入。
- 覆盖非空输出目录的 `--force` 行为。

## 4. CLI 接口

```text
eli loadscreen bake <IMAGE> --directory <DIRECTORY> [--slices <COUNT>] [--jobs <COUNT>] [--quality <0..=100>]
```

参数定义：

| 参数 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `<IMAGE>` | 是 | 无 | 输入静态图片路径 |
| `--directory <DIRECTORY>`、`-d` | 是 | 无 | 烘焙结果目录 |
| `--slices <COUNT>`、`-s` | 否 | `8` | 0% 到 100% 之间的切片数量，最终生成 `COUNT + 1` 张图片 |
| `--jobs <COUNT>`、`-j` | 否 | 逻辑处理器数量 | 并发处理的最大 job 数量，必须大于 0 |
| `--quality <QUALITY>`、`-q` | 否 | `90` | 有损 WebP 质量，合法范围为 `0..=100` |

`--slices` 的合法范围为 `1..=1000`。上限与 0.1% 精度的文件名标记一致，可保证每个切片具有唯一进度文件名。

示例：

```text
eli loadscreen bake wallpaper.jpg -d ./baked
eli loadscreen bake wallpaper.png --directory ./baked --slices 20 --jobs 4 --quality 85
```

命令成功后应打印输出目录、图片数量、输入分辨率和总耗时。错误信息写入标准错误流，并包含发生错误的源路径或目标路径。

## 5. 输入图片

### 5.1 支持格式

首版支持以下静态格式：

- JPEG
- PNG
- WebP
- BMP
- TIFF
- ICO
- TGA

明确不支持 GIF。即使 GIF 只包含一帧也应拒绝，不采用“读取第一帧”的隐式行为。WebP 和 PNG 只支持静态图片，动画 WebP 和 APNG 必须在解码前拒绝。其他能够被底层库偶然识别、但未列入上述清单的格式同样应拒绝，以保持接口稳定。

格式识别优先使用文件内容；对于无法可靠通过文件内容识别的格式，可使用扩展名作为受控后备。扩展名比较不区分 ASCII 大小写。

### 5.2 校验

在创建输出内容前必须完成以下校验：

- 输入路径存在且为普通文件。
- 输入格式位于支持清单中。
- 图片可以完整解码。
- 图片宽度和高度均大于零。
- 解码后的尺寸和内存需求未超过实现定义的安全限制。
- 输入路径不得位于最终输出目录内部，以免目录发布或后续清理影响输入。

损坏图片、伪装扩展名和超出资源限制的图片必须返回明确错误，不得 panic。

### 5.3 分辨率与方向

输出图片不得进行缩放或裁剪，必须保留输入图片的像素规模。若输入包含有效的 EXIF 方向信息，应在模糊前应用方向变换；旋转 90° 或 270° 时允许宽高交换，但不得减少像素数量。

## 6. 切片与文件名

设切片数量为 `N`，图片索引为 `i`，其中 `0 <= i <= N`：

```text
progress(i) = i / N
progress_mark(i) = round(i * 1000 / N)
```

`progress_mark` 表示精确到小数点后一位的百分比，并通过省略小数点得到整数标记。实现必须使用整数运算完成四舍五入，避免浮点误差影响文件名。

文件名格式固定为：

```text
lsbp_{progress_mark:04}.webp
```

其中 `lsbp` 表示 LoadScreen Baked Picture。

默认 `--slices 8` 的完整输出为：

```text
lsbp_0000.webp
lsbp_0125.webp
lsbp_0250.webp
lsbp_0375.webp
lsbp_0500.webp
lsbp_0625.webp
lsbp_0750.webp
lsbp_0875.webp
lsbp_1000.webp
```

`lsbp_0000.webp` 是最模糊图片，`lsbp_1000.webp` 是完全清晰图片。所有文件名按字典序排列时必须与播放顺序一致。

## 7. 模糊模型

### 7.1 目标强度

每一帧的目标高斯模糊强度定义为：

```text
sigma(i) = sigma_max * (1 - i / N)
sigma_max = max(1.0, min(width, height) / 32.0)
```

因此 sigma 随进度严格线性递减：

- 0% 使用 `sigma_max`。
- 100% 使用 `0`，不执行模糊。
- 相邻切片的目标 sigma 差值相等。

`sigma_max` 的比例需要使用至少一张 1080p 和一张 4K 实际壁纸进行视觉验收；首版不提供调整 sigma 的 CLI 参数。若验收后调整比例，必须同步更新相关测试和本文档。

### 7.2 处理策略

首版采用“每张模糊图片都从同一份规范化原图独立生成”的策略，不对已经编码的 WebP 进行解码后继续模糊，也不依赖其他 job 的输出。

模糊器优先采用线性时间的近似高斯模糊算法，使单帧处理复杂度接近 `O(width * height)`。整体计算复杂度目标为 `O((N + 1) * width * height)`。

100% 清晰帧绕过模糊器，直接进入 WebP 编码。若底层算法对非常小的 sigma 没有有效变化，可以跳过对应模糊计算，但仍必须生成独立的进度文件。

首版以烘焙速度为优先，不要求将 sRGB 转换为浮点线性光空间。带透明通道的图片必须使用正确的预乘 alpha 模糊流程，避免透明边缘产生明显黑边或色边。

### 7.3 后续可评估的渐进优化

若基准测试表明独立模糊仍是主要瓶颈，可从 100% 清晰帧向 0% 最模糊帧反向生成，并根据高斯方差可加性计算每一步的增量 sigma：

```text
sigma_delta = sqrt(sigma_target^2 - sigma_current^2)
```

该优化只能在内存像素缓冲区之间执行，不得使用已经编码的 WebP 作为下一步输入。启用前必须证明其输出单调性、视觉连续性和性能均优于独立生成方案。

## 8. WebP 编码

所有输出使用有损 WebP 编码，默认质量为 `90`。用户可通过 `--quality` / `-q` 指定 `0..=100` 的整数质量；`0` 优先最小体积，`100` 优先最高有损质量。质量 `100` 仍属于有损编码，不表示无损模式。

编码由 `webp` crate 调用 libwebp 完成，并与图像解码依赖一起受 `loadscreen-bake` feature 控制；关闭 feature 时不得编译或链接 libwebp。

验收时必须记录：

- 1080p 默认 9 张图片的总烘焙时间和输出体积。
- 4K 默认 9 张图片的总烘焙时间和输出体积。
- 模糊、编码、文件写入分别占用的时间。

验收时应重点比较：

- 与无损结果的视觉差异，特别是渐变、文字附近和透明边缘。
- 总目录体积。
- 编码耗时。
- libwebp 对 Windows、Linux 和 macOS 构建时间及产物体积的影响。

## 9. 并发和实时 job 进度

### 9.1 job 模型

每一张输出图片是一个独立 job，包括：

1. 获取共享的只读原图缓冲区。
2. 按目标 sigma 生成图片；100% 帧跳过此步骤。
3. 编码 WebP。
4. 写入该 job 的临时文件。
5. 将临时文件原子发布到暂存目录中的最终文件名。

某个 job 失败后，应停止领取新的 job，并等待已经运行的 job 安全结束。最终不发布整个目标目录，并统一返回最先发生的主要错误以及失败 job 的进度标记。

### 9.2 并发窗口

省略 `--jobs` 时使用当前系统可用的逻辑处理器数量。实际并发数取逻辑处理器数量和待处理 job 数量中的较小值，且不得小于 1。

显式指定 `--jobs` 时，实际并发数取指定值和待处理 job 数量中的较小值。高分辨率图片的每个并发 job 都需要独立图像缓冲区，设置过大的值可能增加内存占用。

最终并发数不得小于 1。不同 job 只共享不可变原图和取消状态；输出文件互不相同，不得共享可变图像缓冲区。

### 9.3 终端进度展示

交互式终端中使用多进度显示，至少包含：

- 一个总体进度：已完成 job 数量、总 job 数量、百分比、总耗时，以及最近完成 job 的文件名和单项耗时。
- 每个正在运行 job 的文件名或进度标记。
- job 当前阶段：`等待`、`模糊`、`编码`、`写入`、`完成`或`失败`。
- 已完成 job 的独立进度行应立即清除，避免切片数量较多时超出终端可视区域；完成信息由总体进度行滚动展示。
- 同时展开的活动 job 明细最多为 8 行；更多 job 仍正常并发处理，并由总体进度行汇总，避免高核心数机器超出终端可视区域。
- 全部完成后保留最终的总体进度行，明确显示总完成数和最后完成的 job。

示意输出：

```text
总体  5/9  [███████████---------] 55.6%  1.8s  lsbp_0500.webp 完成 · 420ms
0125  模糊中
0250  编码中
0375  写入中
```

进度信息写入标准错误流，成功摘要写入标准输出流，避免管道用户无法单独获取最终结果。

非交互式终端或重定向环境中不得输出光标控制序列，应退化为稳定的逐行事件：

```text
[2/9] lsbp_0125.webp completed in 420ms
```

进度刷新需要限频，避免刷新本身显著拖慢图像处理。建议交互式刷新频率不高于每秒 10 次。

## 10. 输出目录、原子性和并发安全

- 输出目录不存在时允许创建。
- 输出目录存在但为空时允许使用。
- 输出目录存在且非空时拒绝执行，不覆盖或删除任何已有内容。
- 所有 job 先写入唯一的同级暂存目录，全部成功后再发布最终目录。
- 单个文件先写入临时文件，刷新成功后再改名为最终文件名。
- 失败时只清理本次创建的暂存内容，不修改用户原有文件。
- 同一目标目录使用跨进程排他锁，避免多个 eli 进程产生混合输出。
- 不同目标目录可以同时烘焙，锁粒度不得扩大到整个工作目录或整个系统。
- 同一进程内的并发 job 应支持取消和结果汇总；不得因为一个 job 失败而 panic 或遗留后台线程。

对于已经存在的空目标目录，应在持有目标锁的情况下完成检查和最终发布，避免检查与写入之间的竞争条件。

## 11. Cargo feature 和编译体积

feature 名称固定为 `loadscreen-bake`。

- `eli-lib` 将图像处理和 libwebp 编码 crate 声明为 optional dependency，并由 `loadscreen-bake` 启用。
- `eli-cli` 使用同名 feature 转发到 `eli-lib/loadscreen-bake`。
- 完整构建默认启用 `loadscreen-bake`。
- PE 精简构建使用 `--no-default-features`，不编译或链接烘焙实现及其额外图片格式依赖。
- feature 关闭时，`loadscreen bake` 命令从 CLI 帮助和解析结果中消失，而不是保留一个运行时错误桩。
- `loadscreen` 未来若增加不依赖图像处理的子命令，只对 `bake` 子命令进行条件编译，不应把整个父命令永久绑定到该 feature。

Windows CLI 现有的 Slint GUI 会间接依赖 `image` 的 JPEG、PNG 能力，因此在当前依赖图中，关闭 `loadscreen-bake` 后仍可能编译基础 `image` crate；但本功能新增的 BMP、ICO、TGA、TIFF、WebP 能力、`webp` / `libwebp-sys` 编码依赖和烘焙代码不会进入精简构建。若未来要求从 PE 构建中彻底移除基础 `image` crate，需要另行将现有 Slint GUI 也置于可关闭的 feature 后。

预期构建方式：

```text
# 完整版
cargo build --release

# PE 精简版
cargo build --release --no-default-features
```

## 12. 代码组织

遵守项目现有的父命令目录约束：

```text
eli-cli/src/command/loadscreen.rs
eli-lib/src/command/loadscreen/mod.rs
eli-lib/src/command/loadscreen/bake.rs
```

CLI 只负责参数解析、调用库入口和打印结果。图片校验、切片计算、文件命名、模糊、并发调度、进度事件、事务发布和错误汇总均由 `eli-lib` 提供。

库层应将进度报告抽象为回调或事件接收接口，不直接依赖具体终端渲染方式。这样 CLI 可以使用终端进度条，单元测试也能稳定验证事件顺序和最终状态。

## 13. 测试与验收

### 13.1 CLI 测试

- 正确解析输入图片、`--directory`、`--slices`、`--jobs` 和 `--quality`。
- `--slices` 缺省为 8。
- `--jobs` 缺省为自动并发，并拒绝 0。
- `--quality` 缺省为 90，接受 0 和 100，并拒绝大于 100 的值。
- 拒绝 0 和大于 1000 的切片数。
- feature 关闭时不存在 `loadscreen bake` 命令。

### 13.2 单元和集成测试

- 8 个切片生成 9 个约定文件名。
- 不能整除 1000 的切片数量按整数规则四舍五入，且文件名唯一、递增。
- sigma 首尾值正确、单调递减且相邻目标差值一致。
- JPEG、PNG、WebP、BMP、TIFF、ICO 和 TGA 输入按支持策略处理。
- GIF 输入被明确拒绝，包括单帧 GIF；动画 WebP 和 APNG 同样被拒绝。
- 输出宽高与应用方向后的输入宽高一致，不发生缩放或裁剪。
- 所有输出均能作为 WebP 重新解码。
- 默认输出包含有损 `VP8 ` 图像数据，并使用质量 90；所有质量档输出均可重新解码。
- 使用高对比测试图验证清晰度随进度标记单调增加。
- 透明图片的模糊边缘不存在明显黑边。
- 非空输出目录不被修改。
- 任一 job 失败时不发布目标目录，也不遗留本次暂存文件。
- 同进程并发 job 正确汇总成功、失败和取消状态。
- 缺省 job 数等于可用逻辑处理器数量并受帧数限制；显式 job 数受帧数限制。
- 两个进程同时烘焙到同一目录时至多发布一套完整结果。
- 两个进程烘焙到不同目录时可以同时成功。
- 进度事件覆盖等待、处理、完成和失败状态；总体完成数不倒退且不超过总数。
- 非交互模式不包含终端控制字符。

### 13.3 跨平台端到端测试

在 `tests/e2e/` 的 Windows、Linux 和 macOS 脚本中验证：

- 默认命令生成 9 张 WebP。
- 显式切片数量、job 数量和质量生成正确文件名、数量与结果信息。
- 输出文件具有有效 WebP 标识。
- GIF 被拒绝。
- 非空目录和并发同目录操作不会产生部分结果。
- 默认 feature 与 `--no-default-features` 构建均通过。

CI 工作流只负责编排并调用上述脚本，不内嵌具体测试实现。

### 13.4 性能验收

性能测试不设置与具体机器绑定的硬编码 CI 时限。实现完成后，在同一台开发机上分别测试 1080p 和 4K 图片，并记录：

- 串行与自动并发的总耗时。
- 模糊、WebP 编码和写入耗时占比。
- 峰值内存。
- 默认质量 90 及边界质量的输出总大小。

自动并发实现必须相对串行基线有可观察收益。如果编码成为主要瓶颈，应分别测量模糊和 libwebp 编码耗时，而不是盲目继续增加模糊线程。

## 14. 后续演进

后续工作按独立需求处理：

1. 根据基准结果评估按高斯方差递增的渐进模糊。
2. 定义 `.bin` 容器格式、版本、校验和图片索引。
3. 实现 LoadScreen 播放器及真实进度到图片标记的选择规则。
4. 视实际使用需求决定是否公开最大模糊强度参数。
